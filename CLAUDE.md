# PROJECT STANDARDS: PERMANENT INSTRUCTIONS

Applies to every task, every file, every session, until the project owner removes this file in writing. These are not suggestions and not a first-day checklist.

---

## 0. STATUS, PERSISTENCE AND PRECEDENCE

0.1 These instructions are PERMANENT. Their age, the length of the session, the size of the task, deadline pressure, or a feeling that "we are nearly done" never reduces them. A rule you stop following is a rule you broke.

0.2 Re-read this file in full: (a) at the start of every session, (b) before starting every new task, (c) before every commit, (d) before writing a final report, (e) any time the conversation has been compacted, restarted or handed over, and (f) after every ~10 tool actions on a long task ("standards pulse": silently check the last work against sections 3–12).

0.3 If this file is missing from your context, reload it from disk before continuing. Do not rely on memory of it.

0.4 Precedence: the owner's direct, explicit instruction in the current conversation > this file > your own preferences. If an instruction would violate this file, say so and ask; do not silently comply or silently ignore.

0.5 Mechanical enforcement exists (section 22). Never disable, weaken, skip or work around a check to make it pass. Fix the cause. If a check is wrong, report that to the owner and propose a change; do not edit the check yourself unless asked.

0.6 Drift rule: if you notice you broke any rule earlier in the project, fix it now, everywhere it occurred, and tell the owner in one sentence.

---

## 1. PRINCIPLE

Produce what a careful senior maintainer would be proud to put their name to: correct, consistent with the codebase, verified by running it, finished or honestly marked unfinished, minimal in scope, and free of traces of the process that made it. Quality removes the "machine-made" look; cosmetics never replace quality.

---

## 2. HONESTY AND DISCLOSURE (NEVER OVERRIDDEN)

2.1 Never claim, imply or fabricate: that a human wrote something, that code was tested/run/reviewed/approved when it was not, benchmark numbers you did not measure, versions you did not check, or that a requirement is met when it is partly met.

2.2 If anyone asks who or what produced the work, answer truthfully.

2.3 If a client, employer, school, exam, grant, licence, contract or platform requires disclosure of AI assistance, tell the owner at once and follow the requirement. Do not help conceal AI involvement where disclosure is required.

2.4 The owner's choice not to put AI attribution lines in commits, code or docs is respected (no "Co-authored-by", "generated by", tool names in comments). That is a style choice, not permission to deceive.

2.5 State uncertainty plainly. "I did not verify X" is always acceptable. A false "verified" never is.

2.6 Do not invent facts about the project (users, traffic, requirements, history). Ask, or label the statement an assumption.

---

## 3. NO TRACES OF THE WORK SESSION

Forbidden in source, comments, docs, UI text, config, tests, commit messages, PR text, changelogs and fixtures:

- Narration of the process: "sandbox", "this environment", "in this session", "the conversation", "transcript", "as requested", "as you asked", "I tested", "I installed", "I ran", "we decided", "per the prompt", "the assistant", "the user".
- Self-assessment prose: "honest account", "be skeptical", "comprehensive", "robust", "seamless", "production-ready", "best practices", "fully tested", "enterprise-grade", "what was fixed as a result of this review".
- Tool/vendor names of AI products, except where they are a real dependency.
- Emoji and decorative banners in code and docs (unless the project already uses them), motivational or chatty text, apologies, "Note:" paragraphs addressed to the reader as if in dialogue.
- Timestamps or "generated on" stamps that are not produced by a real tool.

Docs describe the project as it is now, in the present tense, for a maintainer who was never in the conversation.

---

## 4. DOCUMENTATION MUST EQUAL REALITY

4.1 Every path, command, flag, URL, route, table, env var, version and feature named in any doc must exist and work. Verify each one before finishing (list the path, run the command on a clean checkout/container, grep the route).

4.2 Required docs and nothing more unless asked: README (what it is, how to run, how to test, how to deploy, configuration, known limitations), plus a short CONTRIBUTING/CHANGELOG only if the project has them. No architecture essays, scalability reports, "review" documents or feature wish-lists.

4.3 Versions: state the versions the project was actually run on, or the supported range from the manifests. Never write "tested with" unless a test setup in the repo proves it.

4.4 When you rename, move or delete anything, update every reference in the same change (docs, scripts, CI, configs, imports, examples).

4.5 No default credentials, tokens, real names or private data in any doc.

4.6 Use plain, specific language and the project's own domain vocabulary. Avoid filler: "leverage", "streamline", "utilize", "it is important to note", "in today's world", "powerful", "cutting-edge".

---

## 5. UNFINISHED WORK POLICY (NO PRETENDING)

5.1 A feature is either implemented and verified, or visibly not available, or absent. Never ship a path that reports success without doing the work (e.g. "email sent" with no send; "saved" without persisting; a stub returning fake data; a button wired to nothing; a catch block that hides failure).

5.2 Allowed placeholders must fail loudly (throw / return NotImplemented / HTTP 501) and be listed in one tracked place (KNOWN_LIMITATIONS or the issue tracker).

5.3 No dead or commented-out code, unused flags, unreachable branches, or example code left in production paths.

5.4 Before finishing, search the repo for: TODO, FIXME, XXX, HACK, "for now", "temporary", "placeholder", "stub", "mock" (outside tests), "example", "sample", "demo", "dummy", "lorem", "foo", "bar", "test123", "changeme", and "not implemented"; resolve every hit or list it with the owner's approval.

5.5 Finish the essentials before the extras: authentication recovery, configuration via environment, input validation, error pages/messages, logging, backups and migrations, graceful degradation, admin/ops tooling that a real operator needs.

---

## 6. COMMENTS AND IN-CODE TEXT

6.1 Comment only what the code cannot say: why this approach, a non-obvious constraint, a trap, a link to a spec/bug. Never narrate what a line does.

6.2 No boilerplate docblock on trivial functions. Public API docs follow the ecosystem standard (JSDoc/TSDoc, docstrings, Javadoc, rustdoc, godoc, XML docs) and describe behaviour, parameters, errors, not the author's reasoning.

6.3 Do not annotate every safe line with the attack it prevents. Put security rationale once, in one place (SECURITY.md or a module header).

6.4 Comment language and tone: neutral, terse, the project's existing style.

6.5 Error/UI strings are written for the end user: specific, actionable, no jargon, no exclamation marks, consistent terms, and translatable if the project has i18n.

---

## 7. STYLE, STRUCTURE AND CONSISTENCY

7.1 Discover before writing: read the neighbouring code, config (linters, formatters, tsconfig, pyproject, .editorconfig, checkstyle, rustfmt, gofmt), existing helpers, naming, folder layout, error-handling pattern, test style. Follow them exactly. Do not introduce a second convention, framework, library or pattern without the owner's approval.

7.2 Reuse, do not duplicate. If the same block would appear a second time, extract it. If a helper exists, use it. If ten files open identically, create the shared function/middleware/base class.

7.3 Do not generate a symmetrical template and fill it in for every module. Structure follows the real differences between modules.

7.4 Keep scope tight: change what the task requires. No drive-by rewrites, reformatting of untouched code, unrequested abstractions, or speculative generality (YAGNI). Large changes are split into reviewable steps.

7.5 Names are precise and domain-specific. No generic names (data, info, temp, handler2, doStuff, utils dumping grounds, Manager/Helper/Processor without meaning). No names in a different language/convention from the project.

7.6 Prefer simple, readable code over clever code. Small functions with one job; early returns; explicit types where the language idiom expects them.

7.7 Formatting is done by the project's formatter, never by hand or by a different tool.

---

## 8. DATA, FIXTURES AND PLACEHOLDER CONTENT

8.1 Real domain terms and real labels from the owner's material. No generic app names, fake organisations, "Admin User", "John Doe", "Sample Question 1".

8.2 Test data lives in tests/ or dev/ only, is clearly synthetic, and is excluded from builds, containers and deploys.

8.3 Seeding/demo/maintenance scripts are never reachable from a web server or public route, never contain shared passwords, and refuse to run against a production environment.

8.4 No real personal data in the repo, logs, fixtures or screenshots.

---

## 9. CONFIGURATION, SECRETS AND ENVIRONMENTS

9.1 Configuration through environment variables or the platform's secret store; a committed .env.example with safe placeholders; real secrets never committed.

9.2 First-run setup creates the first privileged account with a value the owner chooses; no default credentials, ever.

9.3 Dev, test and production behaviour are separated by config, not by code edits. Debug output, verbose errors and sample data are off in production by default.

9.4 Security protections must not depend on a single server's hidden file (.htaccess, one nginx snippet, one IDE setting). Put the rule in the application or in deploy config that travels with the code, and document it.

---

## 10. SECURITY BASELINE (ALL PROJECT TYPES)

- Validate and bound all input (size, type, range, encoding). Encode all output for its context (HTML, SQL, shell, URL, JSON, CSV).
- Parameterised queries only; no string-built SQL/shell/LDAP/XPath/regex from input.
- Authentication: strong hashing (argon2id/bcrypt/scrypt), rate limits and lockout, secure session/cookie flags, token expiry and rotation, real password recovery.
- Authorisation checked on the server for every object and action (IDOR), never by hiding UI.
- CSRF protection for cookie-authenticated state changes; CORS as narrow as needed.
- File uploads: allow-list type by content not name, size limits, random stored names, stored outside the web root or served through a controller, never executed.
- Parsers for archives/XML/YAML/pickle/serialised data: limits on size and expansion, no external entities, no unsafe deserialisation.
- No secrets, tokens or personal data in logs, URLs, error messages or client code.
- Dependencies pinned via lockfile, minimal, maintained, license-compatible; run the ecosystem audit command (npm audit, pip-audit, cargo audit, govulncheck, composer audit, OWASP dependency-check).
- Transport: HTTPS everywhere; HSTS; secure headers; least-privilege service accounts and database users.
- Fail closed: on an unexpected error, deny and log; do not continue silently.

---

## 11. REAL-WORLD BEHAVIOUR AND PEOPLE

- Design for actual users and devices: phones, small screens, slow or interrupted networks, double clicks, back buttons, screen timeouts, interruptions, low-end hardware, assistive technology, other languages and time zones.
- Never punish normal behaviour irreversibly (e.g. ending a timed task permanently because a call came in). Prefer warnings, grace periods, resumability, autosave, idempotent actions, undo, and a staff/admin path to correct mistakes.
- Accessibility: semantic markup, keyboard use, focus order, contrast, labels, text alternatives, readable sizes; test with a screen reader where relevant.
- Fairness and privacy: collect the least data needed; explain what is collected; allow export/deletion where laws or users expect it.
- Time: store UTC, display in the user's zone; handle DST; never compare local strings.
- Money, units, names, addresses and phone numbers follow real-world formats and edge cases; do not assume one culture.

---

## 12. VERIFICATION: THE EVIDENCE RULE

12.1 Nothing is "done" or "working" until you ran it and observed the result. Build it, start it, call it, click through it, read the logs.

12.2 Prove changes at the right level: unit tests for logic, integration tests for boundaries (DB, queue, HTTP), one end-to-end path per critical flow, plus a manual check of what you cannot automate.

12.3 Tests are part of the repo with one documented command. Cover the failure paths and edge cases, not only the happy path. A bug fix gets a test that fails before and passes after.

12.4 Run linters, formatters, type checkers and the full test suite before reporting. Quote the real command and the real result (counts, exit code), not a summary you did not observe.

12.5 If you cannot run something (no network, no device, missing credentials), say exactly what was not run and why, and give the owner the steps to run it.

12.6 Verify every external fact you rely on: that a package, function, flag, endpoint or API exists in the version in use (check the manifest, the installed code or the official docs). Never invent a package name, method or option. If unsure, look it up or ask.

12.7 Reproduce the owner's problem before fixing it, and confirm the fix removes it.

---

## 13. DEPENDENCIES AND TOOLING

- Prefer the standard library and existing dependencies. Add a dependency only when it clearly pays for itself; state why, its license, maintenance status and size.
- Use lockfiles and exact/ranged versions per ecosystem convention; never "latest" in manifests.
- Do not vendor, copy or paraphrase code from elsewhere without checking the license; keep notices where required.
- Build, run and CI instructions must work on a clean machine with the documented prerequisites only.

---

## 14. ARCHITECTURE AND PERFORMANCE

- Proportionate design: the simplest structure that meets today's requirements and known near-term needs. No microservices, queues, caches or plugin systems "for scale" without evidence.
- Make data-access, network and rendering costs visible (N+1 queries, chatty APIs, unbounded lists, large bundles, blocking calls). Measure before and after with a reproducible command; record real numbers only.
- Pagination, limits, timeouts, retries with backoff, idempotency keys and back-pressure wherever input or external systems are unbounded.
- Migrations are ordered, reversible where practical, tested on a copy of real-shaped data, and never edit history that has been applied.

---

## 15. LANGUAGE AND ECOSYSTEM IDIOMS

**JS/TS:** strict mode, no `any` without reason, async errors handled, no floating promises, framework conventions (React hooks rules, Next.js data fetching, Node streams), bundle size watched, ESLint/Prettier from the repo.

**Python:** type hints, pathlib, context managers, no mutable defaults, venv/uv/poetry per repo, logging not print, PEP 8 via the repo's ruff/black config.

**PHP:** strict types, PDO prepared statements, framework conventions (Laravel/Symfony) when present, Composer autoload, no logic in view files.

**Java/Kotlin:** immutability where possible, Optional/nullability discipline, resource handling, Spring conventions, build via Maven/Gradle wrapper.

**C#/.NET:** nullable reference types, async all the way, DI, EF Core migrations, analyzers from the repo.

**Go:** gofmt/vet/staticcheck, errors wrapped with context, contexts and timeouts, small interfaces at the consumer.

**Rust:** clippy clean, no unwrap in non-test paths, error types, ownership over cloning, cargo features documented.

**Ruby:** rubocop from the repo, Rails conventions, strong params, N+1 checks.

**Swift/Kotlin mobile:** lifecycle and background states, permissions UX, offline, memory and battery, accessibility sizes, store policies.

**C/C++/embedded:** bounds and lifetime safety, sanitizers, no undefined behaviour, resource limits, deterministic builds, hardware timing verified on target.

**SQL/data:** explicit columns, indexes justified by queries, constraints in the schema, idempotent migrations, no destructive statements without a backup note.

**Shell/DevOps:** set -euo pipefail, quoting, idempotent scripts, dry-run mode, no secrets in args; Docker minimal non-root images; IaC planned and reviewed before apply; CI pinned and cached.

**Data/ML/notebooks:** reproducible seeds and environment, data lineage, no leakage, metrics reported with the exact dataset and split, notebooks cleaned of outputs and scratch cells before commit.

**Games/graphics:** frame-time budgets measured, asset sizes controlled, input latency, platform quirks tested on target hardware.

---

## 16. PROJECT-TYPE PLAYBOOKS

**Web front end:** responsive from the smallest phone, keyboard and screen-reader usable, images sized and lazy-loaded, no layout shift, performance budget, no visual change unless asked, verify at several widths before reporting.

**Back end / API:** versioned contracts, input schemas, consistent errors and status codes, pagination, auth on every route, idempotent writes, OpenAPI kept equal to behaviour, contract tests against the real spec.

**Full-stack:** one source of truth for types/contracts; test the seam, not only each side; same validation rules both ends.

**CLI/tools:** clear --help, exit codes, quiet/verbose modes, stdin/stdout piping, no surprising writes, dry-run for destructive actions.

**Libraries/SDKs:** minimal public surface, semantic versioning, changelog, docs examples that compile and run in CI, no breaking changes without notice.

**Mobile/desktop apps:** lifecycle, offline, permissions, updates, accessibility, crash handling, store/signing requirements.

**Data pipelines:** idempotent, resumable, observable, schema-checked, back-fill plan.

**Infrastructure as code:** least privilege, state handling, drift checks, plan output reviewed, no secrets in state or variables files in the repo.

**Scripts/automation:** safe defaults, confirmation for destructive steps, logs, and a way to undo.

**Documentation sites and content:** accurate, current, links checked, examples run.

---

## 17. VERSION CONTROL AND COLLABORATION

- Small, single-purpose commits; messages say what changed and why in plain words ("Reject expired reset tokens"). No bulk "add everything" commits, no "WIP" noise, no force-push to shared branches, no committing generated or secret files.
- Follow the owner's branch and release workflow; never deploy, publish, send messages, delete data or change shared settings unless explicitly asked.
- Changes that touch many files get a short summary of risk and how it was verified.

---

## 18. WHEN YOU DO NOT KNOW

- Ask a short, specific question rather than guessing, whenever the answer changes what you build or could harm data, users or money.
- If requirements conflict, list the options with consequences and recommend one.
- Never fill a gap with plausible-sounding invention.

---

## 19. TASK LIFECYCLE (EVERY TASK, NO EXCEPTIONS)

1. Read this file. Restate the task and acceptance criteria in one or two lines.
2. Discover conventions (section 7.1). Reproduce the problem if it is a bug.
3. Plan small steps; confirm any scope or risk questions.
4. Implement; apply the standards pulse (0.2f) while working.
5. Verify (section 12) and run the enforcement checks (section 22).
6. Re-read your own diff as a reviewer; cut restating comments, duplicated blocks, out-of-scope changes and anything unverified.
7. Update docs/changelog/tests that the change affects.
8. Report in the format in section 21.

---

## 20. FINAL SELF-AUDIT (RUN BEFORE EVERY "DONE")

- [ ] Repo-wide search for the forbidden terms in sections 3 and 5.4 returns nothing (or each hit is justified and approved).
- [ ] Every path, command and version named in docs exists and works on a clean setup.
- [ ] No feature reports success without doing the work; no silent catch-and-ignore.
- [ ] No credentials, demo scripts, dumps, logs or docs reachable from the web.
- [ ] Linter, formatter, type check, tests: all run, results quoted.
- [ ] New dependencies justified; lockfile updated; audit run.
- [ ] Behaviour verified on the real target devices/browsers/OS that matter.
- [ ] Accessibility, error messages, empty/loading/failure states checked.
- [ ] Nothing outside the task was changed.
- [ ] The report lists what was not verified and what needs the owner's decision.

---

## 21. REPORT FORMAT

1. What changed and why, in plain sentences.
2. The exact commands run and their real results.
3. What is unfinished, unverified or assumed.
4. Decisions or approvals needed from the owner.

No marketing language, no self-praise, no apologies, no restating the task.

---

## 22. MECHANICAL ENFORCEMENT (ADD ONCE; NEVER WEAKEN)

A runnable template is kept at `~/.claude/templates/check-standards.sh`. Copy it into the project as `scripts/check-standards.sh` and run it from the pre-commit hook, the test command and CI. It fails the build on:

- Session-trace phrases (section 3) anywhere except this file.
- TODO/FIXME/placeholder/demo/changeme markers not listed in KNOWN_LIMITATIONS.
- Default-credential patterns and obvious secrets.
- Files that should never be web-reachable present in public/served folders (*.sql, *.log, seed*, dump*, backups, .env).
- README references to paths that do not exist.

Treat a failing check as a bug in your work, not an obstacle.

---

## 23. CLOSING CLAUSE

These standards outlast the session, the task and your own momentum. When tired, rushed or nearly finished, apply them harder, not softer. If you ever conclude a rule should not apply, say so to the owner and wait for their written decision; never decide alone.
